# Интелигентна обработка на потребителски запитвания

Минимален прототип (Node.js + TypeScript), който приема текстово запитване, определя категорията му и връща структуриран JSON:

- **Технически проблем** (`technical_issue`)
- **Достъп или регистрация** (`access_registration`)
- **Учебно съдържание** (`learning_content`)
- **Друго** (`other`)

Подходът е **хибриден**: бързи и обясними правила се справят с ясните случаи, а несигурните се подават към AI модел. Ако AI услугата не е налична, системата продължава да работи само с правилата и маркира несигурните резултати за ръчен преглед.

## Стартиране

Изисквания: Node.js 22+ (тествано с 22 и 24).

```bash
npm install

npm test                 # 35 теста
npm run demo             # примерите от заданието + гранични случаи (само правила)
npm run demo -- --ai=mock             # правила + примерна (mock) AI услуга
npm run demo -- --ai=mock --ai-down   # симулира недостъпна AI услуга

npm run classify -- "Видеоурокът по математика не се зарежда."   # CLI

npm run dev              # HTTP API на http://localhost:3000 (само правила)
npm run dev:mock         # HTTP API с mock AI
```

За реален AI (по избор):

```bash
# bash/zsh
AI_PROVIDER=anthropic ANTHROPIC_API_KEY=... npm run dev
# PowerShell
$env:AI_PROVIDER="anthropic"; $env:ANTHROPIC_API_KEY="..."; npm run dev
```

Всички настройки са в [.env.example](.env.example). Production build: `npm run build && npm start`.

### HTTP API

```bash
curl -X POST http://localhost:3000/api/classify \
  -H 'content-type: application/json' \
  -d '{"text": "Как мога да променя имейла на профила си?"}'
```

```json
{
  "category": "access_registration",
  "categoryLabel": "Достъп или регистрация",
  "confidence": 0.92,
  "source": "rules",
  "needsReview": false,
  "signals": ["профил/акаунт", "имейл", "промяна на данни"]
}
```

| Поле | Значение |
|---|---|
| `confidence` | Ориентировъчна оценка 0..1 (не е калибрирана вероятност). |
| `source` | `rules` – решено от правилата · `ai` – решено от AI · `rules-fallback` – AI е недостъпен, върнат е резултатът от правилата. |
| `needsReview` | `true` → запитването да се прегледа от човек. |
| `signals` | Кои фрази/думи са засечени от правилата – прави решението обясними. |
| `reason` | Кратко обяснение (от AI или при fallback). |

**Грешки** (празен/невалиден вход) се връщат в същия структуриран вид, без да се хвърля изключение:

```json
{ "error": { "code": "EMPTY_INPUT", "message": "Запитването е празно." } }
```

| Код | HTTP | Случай |
|---|---|---|
| `EMPTY_INPUT` | 400 | празен текст или само интервали |
| `INVALID_TYPE` | 400 | липсващо поле или не е string (`null`, число, обект…) |
| `NO_MEANINGFUL_TEXT` | 400 | само символи, напр. `?!?!` |
| `INVALID_JSON` | 400 | невалиден JSON в тялото |
| `TOO_LONG` | 413 | над 2000 символа |

## 1. Технически подход и аргументация

| Подход | Плюсове | Минуси |
|---|---|---|
| Само правила | евтино, мигновено, детерминирано, обяснимо, без външна зависимост | чупливо при перифрази, правописни грешки и смесени запитвания |
| Само AI | разбира свободен език | цена и латентност на всяка заявка, външна зависимост, по-трудно за тестване и обяснение |
| **Хибрид (избран)** | правилата покриват масовите случаи; AI само за „сивата зона“; системата работи и без AI | две части за поддръжка |

Защо хибрид:

- **Цена и скорост.** Повечето запитвания в образователна платформа са повтарящи се (парола, вход, „не се зарежда“). Те не се нуждаят от модел.
- **Надеждност.** Класификацията е на критичния път на обработката – AI авария не бива да спира приема на запитвания.
- **Обяснимост.** `signals` показва на екипа защо е избрана категорията.
- **Безопасност.** AI моделът може да върне само една от четири категории; всичко друго се отхвърля при валидацията. Текстът на потребителя се подава в `<inquiry>` тагове и се третира като данни (защита срещу prompt injection).

Ключов детайл в правилата: шаблоните за **интенция** („не се зарежда“, „не мога да вляза“) тежат повече от шаблоните за **тема** („математика“, „урок“). Затова „Видеоурокът по математика не се зарежда“ е технически проблем, а не учебно съдържание. Увереността зависи от **разликата** между първата и втората категория, така че смесените запитвания получават ниска оценка и се подават към AI. Освен това, ако втора категория има собствено доказателство (≥ 2 точки, т.е. истински сигнал, а не само тема), запитването се подава към AI **дори при висока увереност**. При недостъпен AI се връща най-силната категория от правилата с `source: "rules-fallback"` и `needsReview: true`.

## 2. Минимална реализация

```
src/
  types.ts            категории, формат на резултата и грешките
  validation.ts       валидация и почистване на входа
  rules.ts            претеглени правила (данни, не код) + оценка на увереност
  ai/
    types.ts          интерфейс AiClassifier (смяна на доставчик)
    anthropic.ts      клиент: таймаут, retry с backoff, строга валидация на изхода
    mock.ts           примерна AI услуга за демо/тестове (може да симулира авария)
  circuit-breaker.ts  спира извикванията към AI при поредни грешки
  classifier.ts       оркестратор: валидация → правила → (AI) → fallback
  server.ts           Express: POST /api/classify, GET /health
  config.ts           избор на AI доставчик от env
  cli.ts, demo.ts     CLI и демонстрация
test/                 35 теста + малък етикетиран набор (dataset.ts)
```

Тестовете покриват: примерите от заданието, валидацията, оркестрацията (AI се вика само при несигурност), fallback при авария, circuit breaker, retry/парсване на AI отговор (с mock `fetch`, без мрежа) и HTTP кодовете.

**Честно за точността:** правилата са тествани на малък набор от 25 ръчно написани запитвания (тест „поне 90%“). Това е регресионна защита, не доказателство за точност в реална среда. Преди production е нужна оценка върху реални, анонимизирани запитвания.

## 3. Архитектура и интеграция

```
Имейл / телефония (транскрипция) / форма
              │
      приемане и нормализация  ──►  опашка (напр. SQS / RabbitMQ / Kafka)
                                          │
                                  ┌───────▼────────┐
                                  │ classifier сервис│  (stateless, N инстанции)
                                  │ валидация → правила │
                                  │      │ несигурно    │
                                  │      ▼              │
                                  │ circuit breaker → AI│
                                  └───────┬────────┘
                                          ▼
              маршрутизация към екип (Технически / Достъп / Съдържание / Общ),
              `needsReview=true` → ръчна опашка за триаж
```

**Интеграция.** Класификаторът е малък stateless сервис зад REST (или консуматор на опашка). Каналите (имейл, телефония) го викат асинхронно: запитването се записва веднага, класифицира се във фонов режим, а резултатът се записва към тикета и определя екипа. Така потребителят не чака класификацията, а платформата не зависи от нея.

**Увеличен брой заявки**
- Сервисът е stateless → хоризонтално мащабиране зад load balancer; при пикове – опашка с няколко консуматора.
- Правилата се изпълняват локално за микросекунди, така че само „сивата зона“ стига до AI – това ограничава разхода и натоварването на външната услуга.
- Допълнително: кеш по нормализиран текст за повтарящи се запитвания, rate limiting и ограничение на паралелните AI заявки, ограничен размер на входа (вече е 2000 символа).

**Недостъпна AI услуга** (вече реализирано в прототипа)
1. таймаут на заявка (5 s) и един повторен опит с експоненциален backoff при мрежова грешка, 429 или 5xx;
2. **circuit breaker** – след 5 поредни грешки AI не се вика 30 s, за да няма натрупване на таймаути;
3. **fallback към правилата** с `source: "rules-fallback"` и `needsReview: true`;
4. За production: запитванията с `rules-fallback` да се класифицират повторно от опашката, когато AI се върне; метрики и аларми за дела на fallback.

**Производствени съображения.** Структурирано логване и метрики (дял на `ai` / `rules-fallback`, латентност, разпределение по категории); премахване на лични данни (имейли, телефони) преди изпращане към външен AI; съгласие с политиката за данни (GDPR); автентикация на API-то.

## 4. Възможности за развитие

1. **Обратна връзка от екипа → непрекъснато подобряване.** Когато служител коригира категорията, корекцията се записва. От тези данни се разширяват правилата, добавят се примери (few-shot) към промпта и се измерва реална точност. Това е най-големият ефект за най-малко усилие.
2. **Приоритет и автоматичен контекст за екипа.** Освен категория, AI може да връща приоритет/спешност (напр. „изпит утре“, „платено, но без достъп“), да извлича данни (клас, предмет, устройство) и да предлага шаблон за първоначален отговор. Така екипът започва със съдържателен тикет, а не със суров текст.

Допълнително, ако се цели и интерфейс: Angular табло за екипа за поддръжка (опашка за ръчен преглед, бутон за корекция на категорията), което се връзва директно с `POST /api/classify` и с обратната връзка от точка 1.

## Ограничения на прототипа

- Правилата са само за български и ключови думи; правописни грешки и латиница („parola“) не са покрити.
- Няма база данни, автентикация, кеш и rate limiting (по условие не са изисквани).
- `AnthropicClassifier` е тестван с mock `fetch`; не е изпробван срещу реалния API в тази среда. Моделът по подразбиране е `claude-haiku-5-5` (конфигурира се с `ANTHROPIC_MODEL`).
